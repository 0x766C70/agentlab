## 4. Surface d’attaque synthétique
1. **Bordure web unique apparente** : Caddy sur 80/443 ; 998 ports filtrés → surface TCP réduite, mais pare-feu/filtrage à confirmer.
2. **Caddy exposé** comme reverse proxy/serveur web ; version non divulguée (`Server: Caddy` / `Via: 1.1 Caddy`), à fingerprint pour CVE.
3. **HTTPS durci** : HSTS preload, `nosniff`, mais headers dupliqués/contradictoires (`X-Frame-Options`, `Referrer-Policy`) → possible chaîne proxy/misconfig à vérifier.
4. **HTTP/3 (QUIC UDP/443)** annoncé via `alt-svc` → surface UDP non testée par le scan TCP.
5. **Routes sensibles potentielles** : `/api/`, `/config`, `/config/`, `/static/` (403), `/robots.txt` ; à évaluer en GET/OPTIONS et par fuzzing de répertoires.
6. **IPv6 présent** (`2001:910:131a:ffff::1`) mais non scanné → vérifier si les mêmes ports sont ouverts en v6.
7. **DNS** : pas de MX/TXT pour ce host ; posture mail (SPF/DKIM/DMARC) devrait être évaluée au niveau du apex `766c70.com` si dans la portée.
8. **Contexte hébergement** : rDNS `vlp.fdn.fr`, IP publique FDN → vérifier attaques par `Host`/virtual-host, headers de proxy, et exposition d’éventuels panneaux d’admin du fournisseur (hors scope strict).

## 5. Recommandations / prochaines étapes
- Passer en **GET** sur `/`, `/robots.txt`, `/config`, `/config/`, `/api/`, et faire un `OPTIONS` ; capturer corps + headers.
- Fuzzing de contenu (ffuf/gobuster/feroxbuster) sur HTTPS, wordlists web + API ; surveiller `405` vs `404` vs `403`.
- Énumération de sous-domaines et SANs du certificat TLS ; scan TLS complet (testssl.sh/sslyze) : cert, SANs, versions TLS, suites, OCSP, session resumption.
- Tester **UDP/443 QUIC/HTTP3** et, si autorisé, le port d’admin Caddy `2019/tcp` (non couvert par le top 1000) ainsi qu’un scan TCP complet si la whitelist le permet.
- Scan IPv6 de `2001:910:131a:ffff::1` si autorisé.
- Fingerprint de version Caddy (pages d’erreur, ACME, comportements HTTP/2/HTTP/3, admin API) puis matching CVE.
- Vérifier la configuration Caddy : `admin` endpoint, `file_server browse`, exposition de `/config`, rate limiting, logs, `Host` header handling, cache/poisoning, et cohérence des security headers dupliqués.
- Ne pas tester au-delà de `maison.766c70.com` sans élargissement explicite de la whitelist.

## 6. Limites de cette passe
- Scan TCP limité au top 1000 ports IPv4 ; aucun scan UDP, aucun scan IPv6, aucun scan de ports > top 1000 (ex. 2019 potentiellement pertinent).
- Outil headers-only : pas de corps GET, pas de cookies/sessions, pas de brute force, pas de TLS handshake complet.
- Aucun sous-domaine ni certificat SAN énuméré.
